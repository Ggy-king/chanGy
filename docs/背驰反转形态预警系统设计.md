### R2 确认/触发区域的"离开"判定 = 连续3根K线创新高制（§`_left_confirm_zone`）
- 旧规则"任何一根K线越过门槛即离开"**作废**（价格在门槛附近徘徊会造成状态反复横跳）。
- 新规则：确认/触发分型（3根K线）之后，出现**连续 3 根已完结K线依次创新高**
  （多头 high 逐根抬升 / 空头 low 逐根下移）才算离开，阶段结束；
  离开后价格**回到区间内**（多头：最新完结K线 high < 门槛）→ 阶段重新显示（可逆不变）。
- 破背驰点 = 假确认实时作废（现价判定），不变。
- 该门控是 **K线级**判定，比画笔快——"图上笔还没画出来但确认已消失"是设计行为。

### R3 状态终结不吞事件（事件流=历史事实留底）
- 状态机模拟中途触发的事件（候选/确认/触发），即使模拟结束时状态已终结
  （价格离开确认区域、假突破作废等），**也必须随 fired 返回并推送**——
  曾因此漏推棉花确认（2026-10-08 事故）。格子显示当前状态，事件流记录发生过的事。
- 指纹 = `pattern|p1|p2`（结构锚）。端点 p3 浮动不入指纹。
- 延续触发（同一指纹再触发，如回调笔延续创新低）→ **原卡片原位更新**：
  保留 `first_time`（首次成立时间）、刷新最新时间并按最新时间排序，
  广播类型 `pattern_alert_update`（手机端忽略此类型，矩阵页按指纹原位刷新）。
  端点没变化不重复广播。

### R4 事件流两条线，与格子完全分离
- **矩阵格子** = 纯实时动态循环，每轮全量重扫按规则推导，**无任何时间限制**——
  60分级别结构走十天半月只要没被规则破坏就一直显示（规则性死亡，不做时间清除）。
- **事件流（推送区）** = 24h**交易时长**内的推送历史（`_is_stale_structure` 仅用于此），
  与格子互不调用、互不影响。
- 矩阵页事件流两个页签：「全部」=候选+确认混排纯时间序 30 条；「确认」=仅确认/触发 20 条。
  手机端固定默认视图，不改。

### R5 监视调度与启动基线
- 交易时段：每 30s 醒来按挂钟对齐拉取——3/5/15/30/60 分钟各按自己的倍数对齐

- **启动时先全量扫一遍基线**（静默不推送→快照统一按时间升序推），之后进入对齐节奏；
  非交易/节假日：启动拉一遍基线后零拉取，每 60s 查开市。
- 旧"15分钟分型买卖点 signal 推送"已废除（§5.5 相关描述作废）；价格预警 alert_loop 保留。

### R7 事件流时间语义与排序（2026-10-08 晚定稿）
- 每张卡片的时间 = **触发时刻 = 端点K线的完结时刻**（K线开始时刻 + 周期）。
  例：60分K线 21:00 开始 → 触发时刻 22:00。**不用K线开始时刻**（用户：60分级别

- 事件流排序 = 按触发时刻**降序**（最新触发的永远在最前），候选/确认无优先级；
  延续触发（同指纹）原卡片更新：时间线刷成最新触发时刻、保留首次成立时间展示，

-forming bar（未完结的原始K线）在数据源头（engine.pattern_snapshot）剔除：
  评估只用已完结K线。不得用"排除最后一根合并K线"代替——forming bar 会与前面的
  完结K线合并成同一根合并K线（一字板全日被合并进一根），整根排除会漏掉已完结
  部分的突破（液化气 2026-10-08 事故）。

### R8 连接死亡判定的品种级豁免（2026-10-08 夜盘首跑发现，当晚二次迭代为品种级时间表）
- 全局 SESSIONS 是所有品种的**并集**，回答不了"某一个品种此刻有没有行情"。
  夜盘时段里无夜盘品种（鸡蛋/生猪/苹果/红枣/尿素）没行情是正常的，15s 收不到
  数据被误判死亡→重建→掐掉夜盘品种的活跃订阅→扫描瘫痪（恶性循环）。
- **最终方案：品种级交易时间表 `trading_sessions.json`**（项目根目录）——
  按品种代码维护（不含合约月份，换月不用改；新增品种加一条即可），
  day 全品种一致，night 按品种（无夜盘=空数组；跨午夜用大于24的小时表示，
  如 25:00=次日01:00）。未收录品种保守视为全时段交易。
- `trading_time.product_in_session(品种)` / `any_product_in_session()` 供查询；
  `tqsdk_data.get_kline`：品种已收市 → 直接回缓存（不等待、不误判、不重建）；
  `_can_recreate`：所有已收录品种均收市 → 禁止重建（取代硬编码 01:00-08:55 窗口，
  未来加原油等 02:30 收市品种自动适配）。
- 基线（启动全量拉一遍）不变：收市品种的历史数据照拉。实测夜盘基线 41 秒、
  连接重建 0 次。
- 有夜盘品种自身收市后（如 PG 23:00-01:00 沪镍仍在交易）**不会**误判：
  其他品种的 tick 会让 wait_update 立即返回、秒回缓存。

## 0. 给实现者的话

这是一个全新的预警系统，用于在**所有品种、所有 K 线级别**上实时识别一种特定的缠论形态
（"下跌背驰 → V 型反转突破前高"，以及它的三买/三卖变体），并在形态第二阶段完成的那一刻推送预警。

设计哲学（用户原话的浓缩）：

1. **不判断"背驰"本身**——任何力度量化都不可靠。唯一可靠的是几何位置条件（见 §3）。
2. **只做可量化的最保守定义**——每一条规则都必须能写成 if 语句，不允许"看起来像"。
3. **多空双向**——每一种形态都有它的镜像（做空版），两个方向都要监视。
4. **只报警，不跟踪**——形态触发即报警并结束。报警之后用户自己等回调接（那笔回调就是标准二买/二卖），跌回 3 下方还是企稳在 3 上方是用户的交易决策，**系统不发"形态失效"通知**。

### 1.1 缠论计算管线（`chanlun/` 包，全部已实现并测试过）

```python
from chanlun import merge_klines, find_fenxing, build_bi, build_zs
```

#### `merge_klines(df) -> DataFrame`
K线包含关系合并。输入 df 需含列：`datetime`(tz-aware Asia/Shanghai), `open,high,low,close,volume`。
输出 merged_df 每行代表一根合并K线，列：

| 列 | 含义 |
| --- | --- |
| `high` / `low` | 合并后高低点 |
| `start_idx` / `end_idx` | 该合并K线覆盖的**原始K线**起止下标（含） |
| `high_idx` / `low_idx` | 组内最高/最低点所在的原始K线下标 |
| `raw_high` / `raw_low` | 组内原始K线的真实最高/最低（= high/low，冗余给出） |
| `init_high` / `init_low` | 组内第一根原始K线的高低（chan.py 增量算法用） |
| `datetime` | 组内第一根原始K线时间 |

#### `find_fenxing(merged_df) -> (top_fx, bottom_fx)`
在合并K线上找分型。每个分型 dict：
`{'idx': 合并K线下标, 'high', 'low', 'datetime', 'start_idx', 'end_idx'}`（start/end_idx 指向该合并K线的原始K线范围）。
顶分型：中间合并K线 high 最高且 low 也最高；底分型对称。

#### `build_bi(top_fx, bottom_fx, merged, **conf) -> list[dict]`
由分型构建笔。六开关见 `chanlun/bi.py` docstring，默认值 = chan.py 原版默认
（`engine.BI_CONF_DEFAULT`）。输出每笔：

```python
{
  'start_idx': 合并K线下标(笔起点), 'end_idx': 合并K线下标(笔终点),
  'direction': 'up'|'down',
  'start_price': 笔起点价格(底分型low/顶分型high),
  'end_price':   笔终点价格,
  'start_datetime', 'end_datetime',
}
```

**重要**：笔端点价格天然就是分型极值价（底分型 low / 顶分型 high）。用户确认：形态比较一律用笔端点价格，不用收盘价。

#### `build_zs(bi_list, zs_extend=True, zs_merge=False, zs_first_bi=False) -> list[dict]`
三笔重叠成枢。输出 `{begin_bi, end_bi, low(ZD), high(ZG), bi_in, bi_out, merged_count}`，下标为 bi_list 下标。本系统第一版**不强依赖**中枢，但走势方向辅助判断会用到（§6）。

## 3. 精确量化规则（伪代码级，逐条可实现）

以下以**做多方向**描述；做空方向把"低/高、向上/向下、大于/小于"全部镜像即可（§3.6）。

设笔列表 `bi[0..n-1]`（`build_bi` 输出，按时间升序）。所有价格比较都用 `start_price/end_price`（= 分型极值价）。

### 3.1 第一阶段（图1 骨架）识别 —— 每当出现新的向下笔完成时评估

取最近三笔 `bi[i-2], bi[i-1], bi[i]`（i 为最新已确认笔下标）：

```
bi[i-2].direction == 'up'     # 1→2 向上笔
bi[i-1].direction == 'down'   # 2→? 向下（作为 1→2 之后必须先向下？）
```

**不对，精确结构是**：1 是低点、2 是高点、3 是低点。即：

```
bi[j]   : up   笔，起点=1(low), 终点=2(high)      # 1→2 必须是一笔（用户确认）
bi[j+1] : down 笔，起点=2, 终点=3(low)             # 2→3 必须是一笔（用户确认）
```

条件逐条：

| # | 条件 | 伪代码 |
| --- | --- | --- |
| R1 | 1→2 是一笔且 2→3 是一笔 | 天然满足（相邻两笔） |
| R2 | 3 创新低 | `bi[j+1].end_price < bi[j].start_price` 即 `p3 < p1` |
| R3 | **背驰段量化（核心）**：3 处底分型的三根合并K线，其最高点全部严格低于 p1 | 见 3.2 |
| R4 | 3 之后尚无向上笔突破 2（否则早该触发了） | 状态机隐含 |

满足 R1~R4 → 进入 `WATCH_LONG` 状态（**不推送**），记录结构 `(p1, p2, p3, t1, t2, t3, 笔下标 j+1)`。

### 3.2 R3 背驰段量化——底分型完整位于 1 下方（最保守定义）

用户原话逻辑：背驰段（2→3）应该力度很深、创很深的低。任何数字化的"深度"都不可靠，
唯一不会漏掉任何背驰段的**最保守**下限是：**3 这个底分型的三根K线，连它们各自的高点都完整地在 1 的低点下方**。
——如果连这个都不满足，那就根本形成不了背驰段，直接排除。

实现（合并K线框架下的等价形式）：

```
设 3 笔终点对应的底分型在 merged 下标 k = bi[j+1]['end_idx']。
取分型三根合并K线：merged[k-1], merged[k], merged[k+1]。
条件：max( merged[k-1]['high'], merged[k]['high'], merged[k+1]['high'] ) < p1
```

**等价性说明**（写给实现者）：合并K线的 `high` = 其覆盖的**全部原始K线**的最高价
（`kline_merge.py` 中 `raw_high = df['high'].iloc[start:end+1].max()`）。
所以"三根合并K线的 high 全部 < p1" ⟺ "分型覆盖范围内的**每一根原始K线**的最高点都 < p1"。
这正是用户要的"原始三根K线（含分型高点）都在 1 下方"的最保守定义，且天然兼容合并K线组内多根原始K线的情况。

边界：若 `k-1 < 0` 或 `k+1 >= len(merged)`（分型贴边），条件无法满足 → 不进入 WATCH。
（贴边分型信息不完整，保守跳过。）

### 3.3 第二阶段（图1 触发）—— 4 突破 2

进入 WATCH_LONG 后，持续监视**所有后续笔**（下标 > j+1）：

```
触发：存在任一向上笔 bi[m]（m > j+1, direction=='up'）满足
      bi[m].end_price > p2        # 严格大于，"哪怕高一个点"
```

- 中间的向上笔没破 2 就继续等（这就是图2 的"多笔"语义，天然涵盖）；
- **触发即推送 `VREV_LONG`**，该结构完成（指纹入已报集合），状态回 IDLE；
- 触发时附带信息：p1/p2/p3、触发笔端点价格与时间、`bi_span = m - (j+1)`（3→4 跨了几笔，供用户参考）。

**图2 的说明**：图2（8→9）与图1 唯一区别是 3→4 之间走了很多笔。统一实现里不需要任何特殊分支——
WATCH_LONG 状态本来就会等所有后续笔，直到某笔突破。9 就是那个最终突破的笔端点。

### 3.4 WATCH_LONG 状态的结构更新（重要）

WATCH_LONG 期间若出现**新的更低低点**（某向下笔 `end_price < p3`）：

- 原 1-2-3 结构作废，以最新三笔重建：新 3 = 新低点，新 2 = 它前面最近的向上笔终点（顶分型 high），
  新 1 = 该向上笔起点（底分型 low），重新检查 R2/R3；
- 若新结构满足 R2/R3 → 继续 WATCH_LONG（更新记录）；不满足 → 回 IDLE；
- 用户原话依据："1 之前若有很多笔比 1 还低，那是中枢扩展，不用管，只找最新的图。"

### 3.5 形态C（三买）—— 图3

骨架（做多方向）：`5(高) → 6(低) → 7(高)`：

```
bi[k]   : down 笔，起点=5(high), 终点=6(low)
bi[k+1] : up   笔，起点=6, 终点=7(high)
```

| # | 条件 | 伪代码 |
| --- | --- | --- |
| C1 | 7 向上突破 5 | `bi[k+1].end_price > bi[k].start_price` 即 `p7 > p5` |
| C2 | **幅度过滤**：6→7 幅度 > 2 × 5→6 幅度 | `(p7 - p6) > 2 * (p5 - p6)` |
| C3 | 尚未有向下笔回调确认/作废 | 状态机隐含 |

C1+C2 满足 → 推送 **`3BUY_CAND`（三买候选）**，进入 `CAND_LONG` 状态。

CAND_LONG 状态的转移：

```
后续出现向下笔完成（第一根 end_price 为该笔低点的笔）：
  若 其 end_price > p5  → 推送 3BUY_CONF（三买确认：回调不回 5 下方）。状态结束。
  若 其 end_price <= p5 → 候选作废（不推送），且该结构与最新走势重建后
                          按-watch A 流程检查（跌破 5 = 新低结构，可能演化为图1）。
```

依据：用户确认"7 强势向上突破之后回调不触碰到 5 = 标准三买"；跌破 5 则回到 5~6 区间，
按图1 逻辑继续演化（此时自动进入 WATCH_LONG 的重建检查）。

**幅度过滤的依据**（用户原话）：图1 的背驰段 2→3 一般走不出 1→2 距离的 2 倍；
反过来 6→7 超过 2 倍 5→6，说明向上动能极强，大概率走三买而不是演化成图1。
这是用户为控制报警频率自己设计的过滤器，**必须实现，参数 2.0 写成常量便于调整**。

### 3.6 镜像（做空方向）

所有条件上下翻转、左右不变：

| 做多 | 做空镜像 |
| --- | --- |
| 形态A：底1-顶2-底3(3<1)，等向上笔破2 → `VREV_LONG` | 形态A'：**顶1-底2-顶3(3>1)**，等向下笔破2 → `VREV_SHORT` |
| R3：底分型三根K线 high 全部 < p1 | R3'：**顶分型三根K线 low 全部 > p1** |
| 形态C：5高-6低-7高(7>5)，(7-6)>2×(5-6) → `3BUY_CAND`；回调低点>5 → `3BUY_CONF` | 形态C'：**5低-6高-7低(7<5)**，(6-7)>2×(6-5) → `3SELL_CAND`；回调高点<5 → `3SELL_CONF` |

做多做空**互相独立、同时运行**，互不干扰（同一时刻同一品种同一级别，
可能既挂着 WATCH_LONG 又挂着 WATCH_SHORT——理论上罕见但允许）。

### 3.7 状态机总图（每个 `symbol + period` 一个实例，多空各一套）

```
IDLE ──检测到A骨架(R1-R4)──→ WATCH_LONG ──任一向上笔end>p2──→ [推送VREV_LONG] → IDLE
  ↑                              │
  │                              └─新低<p3──→ 重建结构 → (满足R2R3? 继续 : 回IDLE)
  │
  ├──检测到C骨架(C1+C2)──→ (直接推送3BUY_CAND) → CAND_LONG
  │                              ├──向下笔end>p5──→ [推送3BUY_CONF] → IDLE
  │                              └──向下笔end<=p5─→ 作废 → 重建检查(WATCH_A逻辑)
  └──（做空对称：WATCH_SHORT / CAND_SHORT）
```

关键实现原则：**状态机每次对"最新完整笔列表"全量重评（幂等）**。
笔会因同性质分型延伸而变化（`build_bi` 中 last_bi['end'] 更新），不要做增量假设——
每次 tick 重算整条管线（毫秒级），把当前笔列表喂给纯函数式的状态评估器，
评估器输出"应处于的状态 + 是否产生新推送"。推送去重靠结构指纹（§5.3），与内部状态无关。
这样实现最简单、重启后天然恢复、不会积累状态 bug。

## 4. 走势方向判断（辅助，非必需）

用户强调实现者要能区分"向上走势类型 / 向下走势类型"。**好消息：形态条件本身已隐含方向**
——形态A 的定义（3 破 1 + 分型全在 1 下方 + 等破 2）只在下降走势末段成立，
形态C 只在上升结构中成立。所以第一版**不需要**独立的走势类型标注。

若未来需要（例如过滤逆大势信号），用户给的算法：
**找最近的中枢（build_zs 的最后一个），看它往哪边被破坏（bi_out 方向），由中枢往后推走势方向。**
中枢向上破坏（向上离开）→ 之后按向上走势处理；向下破坏 → 向下。此条留作扩展，第一版不做。

## 5. 监视系统架构

### 5.1 新模块

```
chanlun/pattern.py      # 纯函数：形态评估器（输入笔列表，输出状态+触发），无任何 IO
engine.py               # 增加 pattern 监视相关函数（拉数+算笔+调评估器）
server.py               # 新增 pattern_loop 后台协程 + 推送
```

形态评估器 `chanlun/pattern.py` 的接口（建议）：

```python
def evaluate(bi_list, reported_keys=None) -> {
    'long':  {'state': 'IDLE'|'WATCH'|'CAND'|'CONFIRMED', 'struct': {...}|None, 'fired': [event,...]},
    'short': {...同构...},
}
# 纯函数、幂等：同样的 bi_list 输入永远得到同样输出。
# reported_keys: 已报过的结构指纹集合（去重用），由调用方持久传入。
# fired: 本次评估相对上次新产生的事件列表（调用方负责推送）。
```

### 5.2 监视循环（server.py 新增 `pattern_loop`，与 periodic/alert_loop 并列）

```
每 30 秒一个 tick（仅 trading_time 内执行）：
  for (sym, period) in 监视清单:            # 见 5.4 分期
    df = tqsdk_data.fetch_kline(sym, period_sec, data_length=2000)   # 内部有缓存/重连
    merged = merge_klines(df); top,bottom = find_fenxing(merged)
    bis = build_bi(top, bottom, merged)     # 默认笔配置，不开任何开关
    result = pattern.evaluate(bis, reported_keys[(sym,period)])
    for event in result.fired:
        构造消息 → manager.remember + await manager.broadcast
```

- 启动第一轮**静默**（只建基线，不推送历史形态）——参照现有 `periodic()` 的启动逻辑。
- 每 tick 全量重拉 2000 根 + 全量重算。单品种单级别毫秒级，15 品种 × 4 级别 = 60 个序列，
  30 秒一轮完全可行。**不要**自己做增量 K 线缓存优化（tqsdk_data 内部已有缓存与重连，别叠加复杂度）。
- fetch 失败（掐线重连窗口）→ 跳过该品种本轮，下轮自然恢复。循环体整体 try/except，绝不让它死掉。

### 5.3 推送与去重

消息 JSON（前端按现有 `signal` 消息的展示路径接入，可加图标区分）：

```json
{
  "type": "pattern_alert",
  "pattern": "VREV_LONG | VREV_SHORT | 3BUY_CAND | 3BUY_CONF | 3SELL_CAND | 3SELL_CONF",
  "symbol": "MA2611", "name": "甲醇", "period": "15",
  "price": 3384.0,            // 触发笔端点价
  "time": "2026-10-05 14:35", // 触发笔端点时间
  "p1": 3300.0, "p2": 3390.0, "p3": 3260.0,   // 结构三点（三买消息给 p5/p6/p7，字段名沿用 p1/p2/p3）
  "bi_span": 3,               // 3→4 跨的笔数（VREV 类）；三买类无此字段
  "ts": 1730000000.0,
  "text": "甲醇 15分 背驰V反(多)：突破3390"    // 预拼接的中文文案
}
```

**结构指纹（去重键）**：`f"{symbol}|{period}|{pattern}|{p1}|{p2}|{p3}"`（价格格式化到最小变动位）。
同一结构指纹只推送一次，进程内 set 记忆即可（重启后首轮静默重建，天然不重复）。
笔因同性质分型延伸而端点微调时，指纹变化会多报一次——可接受（价格变了本质是新信息）。

### 5.4 监视清单分期（控制 free-api 掐线风险）

| 期 | 范围 | 说明 |
| --- | --- | --- |
| 第一期 | 全品种 × `{'5','15','30m','60'}` | ≈60 序列，30s 一轮 |
| 第二期 | 加 `'daily'`（信号少、计算省） | |
| 第三期 | 加 `'30','1','3'`（30秒/1分/3分） | 订阅量翻倍，实测掐线后决定是否分批轮询 |

参数写成 `config.PATTERN_PERIODS`，方便用户自己增删。

### 5.5 旧预警的处置（用户明确指示）

- `periodic()` 15 分钟循环里的**分型买卖点推送停用**（"咱现在做那个预警就可以完全放弃掉了"）。
  保留每 15 分钟的总览刷新（页面数据还靠它），只去掉"新 signal 消息"的检测与广播部分。
- `alert_loop()` 用户手设价格预警 **保留不动**。
- 本系统是**新预警**，消息类型 `pattern_alert`，与上述两者并存。

## 6. 需要实现者注意的边界情况（完全分类）

1. **3 之后继续创新低**：按 §3.4 重建结构，以最新为准。不做中枢扩展分析（用户明确"不用管"）。
2. **笔端点延伸**：`build_bi` 会把同性质分型并入最后一笔终点（如向上笔创更高高点）。
   每次全量重评天然处理；指纹去重防止重复推送。
3. **分型贴边**（`k-1<0` 或 `k+1>=len(merged)`）：R3 无法评估 → 不进 WATCH。保守跳过。
4. **WATCH/CAND 同时存在多个历史结构**：只保留最新一个（新低重建机制保证）。多空两套互不影响。
5. **突破与回调发生在同一根K线**：以笔列表为准（笔没确认就不算）。宁可晚一根K线，不可提前。
6. **非交易时段**：循环 sleep 跳过；周末/节假日数据不变，评估幂等无副作用。
7. **重启**：首轮静默建基线 → 不会把历史形态当新预警轰炸用户。
8. **品种换月**（CONTRACT_MAP 变化）：指纹含 symbol，自然隔离。
9. **两根相邻中枢时间重叠**：与本系统无关（那是展示层的事），形态只用笔端点。

## 9. 全级别并行监控矩阵页面（2026-10-06 增补，用户需求）

### 9.1 为什么需要这个页面（用户的使用流程）

弹窗/消息流的问题：用户不可能时刻盯着，错过一条就没了。用户的真实工作流是：

因此矩阵页面与弹窗消息是**互补**的：WebSocket 消息照发（§5.3），但**主交付物是这个页面**。

  之后 WebSocket 收 `pattern_state` 增量消息（单个 cell 变化推一条）实时更新对应格子。
- **提醒增强**（用户盯着页面的场景）：`fired_a`/`cand_b`/`conf_b` 发生时，页面播放一声短提示音
  （Web Audio API，无需资源文件）+ 页面标题闪烁 `🔴 甲醇15分 A类`；浏览器 Notification 授权后同时弹系统通知。全部前端实现，server 无改动。

### 9.4 页面底部区域（用户犹豫的部分，建议方案）

示意图底部三张"分级操作卡片"（按级别列止损/仓位/持有）**不做**——那是交易计划，不是系统职责，
而且写死规则会误导。底部改为一个**实时事件流**（最近 50 条，新在上）：

```
14:35  🔴 A类  甲醇 15分   V反(多) 突破3390     [3→4跨2笔]
14:21  🟡 B类  螺纹 30分   三买候选 3320        [幅度2.3×]
13:58  🟢 B类  白糖 60分   三买确认 5612
```

每条 = 一次状态转移的审计记录（服务端 remember 的 pattern 消息复用）。
用户"更紧急的东西放底部"的诉求由此满足：**最新、最需要立即看的事件永远在最下面一张卡的位置**，
且比固定三张卡信息密度高。若用户日后想加"操作建议卡"，在此区域追加即可。

### 9.5 对 §5 的回溯修改

- §5.2 `pattern_loop` 每次评估后：除 fired 事件外，还要 diff 单元状态，
  变化的格子广播 `{'type':'pattern_state', 'cell': {...}}`；并在内存 dict `_pattern_cells` 里保存全量（`/api/pattern_matrix` 读取）。
- §5.3 的消息推送照旧（`pattern_alert` 进消息流/历史）；矩阵页面两种消息都监听。
- 监视清单（§5.4）的分期不变，矩阵行列直接由它驱动——**改 config 就能加减行列，页面零改动**。
